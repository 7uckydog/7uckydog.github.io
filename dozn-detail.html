DOZN BackOffice

DOZN은 전국 105대 키오스크에서 매일 현금과 거래가 발생하는 구조로, 운영·정산·모니터링이 정교하게 맞물려야 합니다. 다만 실제로는 상당 부분이 이메일·유선·엑셀로 처리되고 있었고, 담당자 부재나 단순 누락이 곧바로 시재 불일치·정산 지연으로 이어지는 구조였습니다.

이 업무들을 도메인 모델로 다시 설계하여 시스템 안으로 옮기는 작업을 진행했습니다. 자산 이동 워크플로우 · B2B 어드민 신규 구축 · 정산 자동화 · 쿼리 전략 전환 · 실시간 운영 대시보드 다섯 가지 축으로 나눠 진행했고, 운영팀·재무팀·경영진이 같은 데이터를 기준으로 움직일 수 있도록 묶는 데 초점을 뒀습니다.

각 작업은 기획서·Figma 검토부터 ERD 설계, 백엔드 개발, 운영까지 전 과정에 직접 참여했습니다. 화면 기획 단계에서 데이터 흐름을 함께 정의하고, 그에 맞는 테이블 구조를 설계한 뒤 구현으로 이어가는 방식이라, 단순 기능 구현이 아니라 요구사항부터 데이터 모델까지 일관된 의도로 묶는 것을 지향했습니다.

아래 다섯 개의 케이스는 그 과정에서 풀어낸 문제와 설계 의도, 핵심 구현 근거, 그리고 도입 후 달라진 점과 배운 점을 정리한 기록입니다.

Case 01

자산 이동 워크플로우 시스템화

전국 105대 키오스크, 평일 일 7건 이상, 회당 최대 3천만원 이상이 움직이는 현금 수송 업무를 상태머신 기반 도메인 모델로 시스템 안에 옮긴 작업입니다.

문제 상황

자산이 움직이는 업무가 시스템 없이 사람 간 커뮤니케이션에 의존하고 있었습니다. 운영 관리자가 이메일·유선으로 수송을 지시하고 작업 결과는 엑셀에 수기로 정리해 공유하다 보니, 업무 흐름 자체가 시스템 바깥에 존재하는 상태였고 다음과 같은 문제가 반복됐습니다.

  • 수송 요청 누락구두·이메일 지시 특성상 수신자가 인지하지 못한 채 지나가는 경우가 있었고, 누락은 추후 시재가 안 맞을 때야 발견됐습니다.
  • 데이터 대사 불일치운영팀 엑셀, 재무팀 엑셀, 어드민 데이터가 따로 관리돼 같은 건이 서로 다르게 기록되곤 했습니다.
  • 담당자 부재 시 단절특정 담당자만 맥락을 아는 작업이 많아, 휴가·외근 시 작업이 멈추거나 잘못된 정보로 진행되는 휴먼 에러가 발생했습니다.
  • 전체 흐름 가시성 부재어떤 키오스크에 어떤 작업이 어디까지 진행됐는지 한 화면에서 볼 수 없어, 매번 개별 확인이 필요했습니다.

해결 과정

자산 운영 관리자·재무팀과 함께 실제 현금 수송이 어떤 순서로 일어나고 각 단계에서 누가 무엇을 결정하는지, 어떤 예외 케이스(긴급 보충·회수·점검 동반 작업)가 있는지 정리한 뒤, 기획·화면 흐름 정의부터 ERD 설계, 구현까지 직접 진행하며 작업의 생명주기를 도메인 모델로 정의했습니다.

  • 상태 전이 제어작업 생명주기(요청 → 진행중 → 정보 입력 → 정보 확인 → 완료 확정, 취소)를 enum의 단계 값(stepOrder)으로 정의하고, 상태를 변경할 때 메모리 값을 믿지 않고 DB에서 현재 상태를 다시 조회해 검증했습니다. 현재 단계에서 바로 다음 단계로 넘어가는 게 맞는지를 확인하고, 단계를 건너뛰는 비정상 전이(요청 단계에서 곧바로 완료로 점프 등)는 예외를 던져 차단했습니다. 동시 요청으로 상태가 이미 바뀐 경우에도 최신 DB 값을 기준으로 판단하도록 한 것입니다.
  • 정합성 검증 응집키오스크 시재, 운영팀 보유 현금, 송금·입금 데이터와의 정합성 검사를 한 곳에 모아, 동일한 검증 로직이 여러 레이어에 흩어져 중복되는 문제를 없앴습니다.
  • 작업 단위 이력화상태·데이터 변경은 JPA Auditing으로 변경 주체와 시점을 자동 적재하고, 현금 수송 고유의 액션(요청·수락·연락·메모·대사 등)은 별도의 전용 이력 테이블에 append-only로 적재해 사후 추적과 책임 소재 확인이 가능하게 했습니다.
  • 알림 분리단계가 바뀔 때마다 담당자에게 자동 이메일이 가도록 하되, 알림을 핵심 트랜잭션과 분리했습니다. 정보 입력·상태 변경 트랜잭션이 정상 커밋된 이후 이벤트 리스너를 통해 비동기로 발송되도록 구성해, 알림 처리가 핵심 비즈니스 트랜잭션의 성능이나 성공 여부에 영향을 주지 않게 했습니다.

특히 기존에 따로 관리되던 사내 보유 시재와 키오스크 실시간 시재 정보에 이 모듈을 연결한 부분이 중요했습니다. 자산 이동이 별개 기능이 아니라 전사 자산 흐름의 한 축이 되도록 묶어, 운영팀과 재무팀이 같은 데이터를 보고 의사결정할 수 있는 기준을 만들었습니다.

수송 요청 누락 월 10건 → 0건으로 사라졌고, 담당자가 부재해도 작업이 멈추지 않고 인계되는 구조가 됐습니다. 흩어져 있던 데이터가 한곳에 모이고 확정된 데이터만 노출되며 월말 시재 대사 작업은 약 10배 빨라졌습니다.

누락 월 10건 → 0건월말 대사 약 10배 단축운영·현송·재무팀 동일 데이터 의사결정

업무를 코드로 옮길 때 가장 중요한 건 '기능'이 아니라 '허용되지 않는 일을 막는 규칙'이라는 걸 배웠습니다. 또한 상태 검증은 메모리에 들고 있던 값이 아니라 그 순간의 실제 DB 상태를 기준으로 해야 동시 요청에도 안전하다는 점을 체감했습니다. 덕분에 담당자가 바뀌거나 요청이 겹쳐도 시스템이 잘못된 진행을 스스로 거부하는 구조가 됐습니다.

Case 02

롯데카드 체크인 서울 어드민 신규 구축
— 인프라부터 AI 협업 워크플로우까지

롯데카드 '체크인 서울' 선불카드 운영을 위한 어드민을, 인프라 구축(DNS·침입차단 결재 포함)부터 AI 협업 개발 워크플로우(하네스 엔지니어링) 설계까지 처음으로 전 영역을 책임진 작업입니다.

문제 상황

롯데카드 측 요청으로 '체크인 서울' 선불카드용 어드민을 신규 제공해야 했습니다. 사내 운영 BO와는 격리된 환경이 필요했고, 기존엔 API 서비스와 화면 서비스를 각각 별도 도메인으로 띄우던 구조였습니다.

이번엔 단일 진입 구조를 시도하고자 했고, 시각디자인·백엔드 베이스인 본인이 처음으로 인프라 전 영역을 책임지는 상황이기도 했습니다. 동시에 AI 협업(바이브 코딩)이 이 프로젝트의 기본 개발 도구가 되면서, AI가 추측 없이 일관된 품질을 내도록 만드는 문서 체계가 코드 이전에 필요하다고 판단했습니다.

  • 인프라가 처음DNS, 침입차단 정책, 서버 자원, 컨테이너 오케스트레이션까지 직접 책임져야 했습니다.
  • 격리된 환경 요구사내 BO와 다른 망/도메인 정책으로 운영되어야 했습니다.
  • AI 협업의 일관성같은 피처를 다시 요청해도 항상 같은 구조의 코드가 나오게 만들어야 했습니다.

해결 과정 — 인프라 직접 구축

  • 결재 프로세스 직접 처리DNS 신청 · 침입차단 정책 결재 · 서버 자원 확보까지 직접 진행. 결재 프로세스를 따라가며 개발기 환경을 처음부터 완성했습니다.
  • Nginx 단일 진입점 + 경로 기반 라우팅별도 도메인을 두 개 두지 않고, 1개 Nginx 인스턴스에서 경로로 분기. /admin-api/* → API 서버 컨테이너, / (그 외) → 화면 서버 컨테이너로 라우팅. DNS·인증서·CORS 관리 비용을 절반으로 줄였습니다.
  • Portainer Stacks 활용컨테이너 그룹을 선언적 정의로 묶어 배포·재기동·롤백 단위를 단순화. 사내 다른 프로젝트와 동일한 운영 환경을 유지했습니다.

해결 과정 — 하네스 엔지니어링 (AI 협업 워크플로우 직접 설계)

AI 협업이 안정적으로 동작하려면 '도구를 잘 쓰는 것'이 아니라 'AI가 추측할 여지를 없애는 문서 체계'가 핵심이라고 판단했습니다. 그래서 프로젝트 시작과 동시에 AI(Claude)와 협업하며 문서 시스템을 설계했습니다.

본인이 한 일은 무엇을 어떻게 만들지(요구사항)와 문서 구조의 큰 틀을 정의하는 것이었고, AI가 그 방향대로 문서를 채우면 본인이 검토·수정·채택하는 흐름이었습니다.

  • 3단 문서 라우터 구조 설계CLAUDE.md(프로젝트 컨벤션)가 harness-engineering.md(루트 문서)를 가리키고, 거기서 상황별 세부 문서로 라우팅하는 구조. AI가 무작정 추측하지 않고 정해진 경로의 문서를 먼저 확인하도록 강제.
  • 약 3,500줄 분량의 문서 체계피처 개발 흐름, 애플리케이션 아키텍처, API 계약, 테스트 하네스, 인증 프로세스, KDoc 컨벤션, PR 체크리스트, 도메인별(광고 등) 워크플로우 문서를 체계화.
  • BDD 기반 피처 개발 워크플로우 정립Feature → Scenario(Given/When/Then) → 실패하는 테스트 → 최소 구현 → 리팩터링 순서로 고정. 시나리오 정의 없이는 코드 생산이 시작되지 않도록 가드.
  • 1 피처 = 1 브랜치 원칙다른 피처 코드를 건드리지 않는 작업 단위 규율을 명문화해, AI가 작업 범위를 임의로 확장하지 않도록 통제.
  • Lightweight CQRS같은 JPA 모델·Repository를 공유하면서 command/query 책임만 분리. 순수 CQRS 오버엔지니어링을 피하되 책임 분리는 유지하는 균형점 채택.
  • Mock 기반 테스트 우선Service 테스트는 Spring context 없이 MockK로 협력 객체 대체. 테스트가 가볍게 돌도록 해 AI가 만든 코드의 검증 사이클을 짧게 유지.

AI 협업은 '도구 활용 능력'의 문제가 아니라 'AI가 추측하지 않도록 만드는 문서 시스템'의 문제라는 것을 체감했습니다. AI에게 코드를 잘 짜게 만들려면, 코드 이전에 무엇을 어떻게 만들지가 문서로 고정되어 있어야 했습니다. AI는 작성 도구이고, 일관성을 보장하는 규칙과 구조는 사람이 설계해야 한다는 점이 핵심이었습니다.

처음 해본 인프라 영역도 결국 결재 프로세스를 따라가면서 한 단계씩 풀리는 일이라는 점, 그리고 별도 도메인을 두 개 두는 대신 Nginx 단일 진입 + 경로 분기로 가는 단순함이 운영 측면에서 얼마나 큰 차이를 만드는지를 직접 체감했습니다.

Case 03

나이스 · 이즐(eZL) 정산 자동화

나이스(일 10건, 구매·충전·출금) + 이즐(주 40건, 상계처리 포함)의 수기 대사·송금 프로세스를, 스케줄러 기반 자동 파이프라인으로 전환한 작업입니다. 월 약 1천만원 규모의 자동 송금이 중복 없이 처리되도록 DB 유니크 제약 + 사전 검증 이중 안전장치를 설계했습니다.

문제 상황

재무팀의 정산·대사 업무는 회사 현금 흐름과 직결되는 핵심 프로세스인데도 거의 전적으로 수작업에 의존하고 있었습니다. 연동 업체가 매일 올려주는 대사 파일을 담당자가 직접 받아, 어드민에 쌓인 거래 내역과 한 건씩 눈으로 비교한 뒤 수기로 송금하는 구조였습니다.

  • 휴먼 에러 누적거래 건수가 늘수록 수기 비교 과정의 누락·중복·오매칭이 비례해 늘었습니다.
  • 담당자 부재 시 지연대사 업무가 특정 담당자에게 몰려 있어, 부재 시 정산이 하루 이상 밀리는 일이 잦았습니다.
  • 누적 데이터 관리 비효율일별 엑셀이 매일 새로 만들어져, 누적 통계나 과거 시점 추적에 상당한 비용이 들었습니다.
  • 업체별 정산 방식의 비표준성가장 큰 난점이었습니다. 일반 승인 거래 외에 당일 승인 취소, 사후 매입 취소, 상계 처리, 수수료 차감 방식이 업체마다 달랐는데, 시스템화되어 있지 않아 계약서 원문이나 과거 이메일 협의 이력을 다시 찾아야 정상 대사가 가능했습니다.

해결 과정

영업팀·재무팀과 함께 업체별 정산·대사 프로세스를 처음부터 다시 분해하고, 계약서·운영 메모·과거 이슈에 흩어져 있던 룰을 한곳에 모아 업체별 정형화된 규칙 셋으로 재정의했습니다. 이 규칙을 바탕으로 처리 단계별 ERD를 직접 설계하고 그 위에 자동 파이프라인을 구현했습니다.

  • 스케줄러-로직 분리별도 스케줄러 전용 애플리케이션에서 cron 기반으로 고도화 백오피스 API를 호출하는 구조로 분리해, 스케줄 변경이나 수동 재실행이 백오피스 비즈니스 로직에 영향을 주지 않도록 했습니다. 정상 케이스는 사람 손을 타지 않고 끝까지 처리되는 게 기본값입니다.
  • 단계별 테이블 분리처리 단계별로 테이블을 나눠 각 단계의 책임과 추적성을 확보했습니다. 파트너사가 보낸 파일을 가공 없이 보관하는 원본 적재 테이블(분쟁 시 원본 대조용), 대사 성공 여부와 거래 단위 데이터를 담는 대사 완료 테이블, 파트너사 구분 없이 정산 금액을 통합 집계하는 정산 집계 테이블, 송금 결과값·재시도 횟수를 담는 송금 완료 테이블로 구성했습니다. 정산 외 사외 송금까지 포함하는 통합 송금 원장에도 함께 적재해 전사 자금 집행 내역을 한곳에서 볼 수 있게 했습니다. 송금 자체는 사내 송금 개발팀과 협업해 처리하며, 그쪽에서 내려주는 결과값과 재시도 이력을 송금 완료 테이블에 적재합니다.
  • 중복 처리 방지돈이 오가는 만큼 중복 송금 방지에 가장 신경 썼습니다. 정산·송금 테이블에 날짜 + 파트너사를 유니크 키로 두어 동일 건의 중복 처리를 DB 레벨에서 차단하고(대사 테이블은 거래 건 단위라 제외), 모든 정산·송금 프로세스 시작 전에 당일 이미 처리된 건이 있는지 사전 검증하는 로직을 두어 스케줄러 중복 실행이나 재실행 시에도 이중 송금이 발생하지 않게 했습니다.
  • 정산 예정일시 기반 송금모든 정산 데이터에 파트너사별 주기를 계산한 정산 예정 일시를 부여하고, 송금 스케줄러가 당일 예정이면서 아직 송금되지 않은 건만 조회해 처리하도록 해, 업체별로 다른 정산 주기를 단일 스케줄러로 일관되게 처리했습니다.
  • 실패 정책대사 실패 시에는 부분 처리 없이 해당 건을 통째로 보류합니다. 실패 원인이 자사 데이터뿐 아니라 파트너사 측 오류일 수 있어(이 경우 대사 파일을 다시 받아야 합니다) 잘못된 데이터로 후속 정산·송금이 진행되는 것을 막기 위한 의도적 설계입니다. 보류 건은 원인 파악 및 조치 후 재진행합니다.
  • 확정-송금 분리자동 대사를 통과한 건이라도 바로 송금되지 않고, 재무팀의 명시적 확정 액션이 있어야 송금되도록 분리했습니다. 자동화의 편의성과 자금 집행 통제권 사이에서 균형을 잡기 위한 의도적 설계입니다. 또한 파이프라인 각 단계 사이에 Slack 알림을 연동해, 불일치 발견 시점을 월말에서 당일로 앞당겼습니다.

정산 업무가 특정 담당자에게 묶이지 않게 되어, 담당자 부재 시에도 대체자의 수기 개입 없이 자동으로 처리됩니다. 불일치 발견 시점이 "월말 정리 중"에서 "당일 슬랙 알림"으로 앞당겨졌습니다. 재무팀이 단순 비교 작업에서 벗어나 예외 케이스 판단·협의 같은 사람이 해야 할 일에 집중할 수 있게 됐습니다.

월 약 1천만원 자동 송금불일치 발견 월말 → 당일담당자 부재에도 무중단 운영중복 송금 0건

돈이 오가는 자동화에서 중요한 건 처리 속도가 아니라 '틀렸을 때 멈추고 추적할 수 있는 구조'라는 걸 배웠습니다. 그래서 실패 시 통째 보류, 단계별 원본 보존, 확정-송금 분리를 의도적으로 선택했습니다. 자동화의 편의와 자금 통제권 사이의 균형이 핵심이었습니다.

Case 04

쿼리 전략 전환과 팀 쿼리 작성 기준 정립

가상계좌 입금 통합 조회 기능을 만들며 부딪힌 디버깅·UNION 한계를 단계적으로 풀어내고, 그 과정에서 SQLQueryFactory와 MyBatis를 팀에 신규 도입하며 쿼리 성격별 작성 기준을 정립한 작업입니다. 현재 내부 어드민 관리자 3명이 동일 기준으로 거래 관련 쿼리를 작성합니다.

문제 상황

가상계좌 입금 내역 조회 기능을 개발하던 중 기존 방식의 한계에 부딪혔습니다.

  • 문자열 조립의 디버깅 난해입금 조회 쿼리가 createNativeQuery에 StringBuilder로 SQL 문자열을 이어붙이는 방식이었습니다. SQL이 단순 문자열이라 컬럼명·괄호·콤마·공백을 틀려도 컴파일은 정상 통과하고, 실제 실행해봐야(런타임) 오류를 알 수 있었습니다. 그마저도 "SQL 문법 오류" 수준으로만 떠서 긴 문자열 어디가 틀렸는지 짚어주지 않았고, 조건이 분기될수록 자바 코드와 최종 SQL의 대응 관계를 추적하기 어려웠습니다.
  • 다중 출처 통합 조회 요구가상계좌 입금원이 더프리(자체 선불카드 충전)와 온라인 환전 신청 등 여러 곳이라, 입금 내역을 한 화면에서 보려면 서로 다른 테이블을 UNION ALL로 합쳐 조회해야 했습니다. 출처가 늘어날수록 쿼리는 더 길고 복잡해질 수밖에 없는 구조였습니다.

해결 과정

"디버깅 가능성"과 "UNION 지원"이라는 두 요구를 동시에 만족하는 방법을 단계적으로 찾아갔고, 그 과정에서 팀의 쿼리 작성 도구 자체를 두 번 확장했습니다.

  • 1차 검토 — JPAQueryFactory의 한계가장 먼저 팀에서 평소 쓰던 JPAQueryFactory(QueryDSL-JPA)를 검토했습니다. 타입 세이프해서 디버깅 문제는 해결되지만, 이건 JPQL로 변환되는 구조라 UNION을 지원하지 않습니다. 다중 출처 통합 조회라는 핵심 요구를 충족할 수 없어 다른 방법이 필요했습니다.
  • 2차 도입 — SQLQueryFactory (팀 최초)그래서 QueryDSL-SQL의 SQLQueryFactory를 팀에서 처음 도입했습니다. JPA(JPQL)를 거치지 않고 실제 DB SQL을 타입 세이프하게 작성하는 방식이라, UNION ALL을 지원하면서도 컴파일 시점에 오류를 잡을 수 있었습니다. 문자열 조립에서 겪던 "어디가 틀렸는지 모르는" 문제와 UNION 미지원 문제를 한 번에 해소했습니다.
  • 한계 인지 — 코드 조립의 복잡도다만 운영하며 또 다른 한계가 보였습니다. 타입 안정성은 좋지만, UNION에 조건이 많이 붙는 통계성 쿼리를 자바 코드로 조립하다 보니 소스가 방대하고 복잡해져, 오히려 SQL 원문보다 읽기 어려워지는 경우가 생겼습니다. "타입 세이프"가 모든 쿼리에서 정답은 아니라는 판단에 이르렀습니다.
  • 3차 도입 — MyBatis (신규 도입)복잡한 통합 조회는 SQL을 원문 그대로 작성하는 게 더 명확하다고 판단해, MyBatis를 도입했습니다. 단순·동적 조건은 QueryDSL로, 길고 복잡한 통합·통계 조회는 MyBatis로 가는 식으로, 쿼리 성격에 따라 도구를 나눠 쓰는 기준을 세웠습니다.
조회 전략 선택 기준 — 쿼리 성격에 따른 도구 분리
// 단순 CRUD·동적 조건  →  JPAQueryFactory (타입 세이프, 가장 간결)
// 다중 테이블 UNION    →  SQLQueryFactory (JPQL 미지원 UNION 처리 + 타입 세이프)
// 길고 복잡한 통계 조회 →  MyBatis (SQL 원문이 더 가독성 높음)

// 가상계좌 입금 통합 조회 — 더프리 충전 + 온라인 환전을 UNION ALL
val union: SubQueryExpression<Tuple> = SQLExpressions.unionAll(
  prepaidChargeQuery,   // 더프리 선불카드 충전 입금 쿼리
  exchangeRequestQuery  // 온라인 환전 신청 입금 쿼리
)

// union 결과를 서브쿼리로 두고 PathBuilder로 별칭(u)을 잡아 조회
val u = PathBuilder(Tuple::class.java, "u")
sqlQueryFactory.query()
  .select(Wildcard.count)
  .from(union, u)
  .fetchOne()

쿼리 성격에 따라 도구를 나눠 쓰는 기준이 생겼습니다. 단순/동적 → JPAQueryFactory, UNION → SQLQueryFactory, 복잡 통계 → MyBatis. 한 번의 선택으로 끝내지 않고 한계가 보일 때마다 다시 판단한 과정이, 팀의 쿼리 작성 기준으로 남아 이후 모든 거래 관련 쿼리에 적용되고 있습니다.

SQLQueryFactory 팀 최초 도입MyBatis 신규 도입팀 쿼리 작성 기준 정립관리자 3명 적용 중

'더 나은 도구'는 고정된 정답이 아니라 쿼리 성격에 따라 달라진다는 걸 체감했습니다. 타입 안정성이 중요한 구간은 QueryDSL-SQL, 복잡한 통합 조회는 MyBatis로 — 한 번의 선택으로 끝내지 않고 한계가 보일 때마다 다시 판단한 과정 자체가, 개인의 해결을 넘어 팀의 쿼리 작성 기준이 됐습니다.

Case 05

실시간 운영 대시보드

8개 페이지 진입 + 엑셀 가공 + 메일 발송을 반복하던 일 30분의 수동 리포트 워크플로우를, 데이터 성격에 맞는 갱신 전략을 설계해 단일 실시간 대시보드로 통합한 작업입니다.

문제 상황

기존 백오피스에 거래 내역, 키오스크 상태, 환율·스프레드 데이터가 다 있긴 했지만 각 정보가 별도 페이지에 흩어져 있었습니다. 데이터는 있는데 한눈에 볼 화면이 없다 보니, 재무팀이 매일 다음을 반복했습니다.

  • 1. 페이지 순차 진입백오피스 약 8개 페이지에 순차로 들어가 데이터 확인 (거래 유형별).
  • 2. 다축 조회 · 다운로드일별·통화별·국가별·키오스크별 거래 내역을 각각 조회·다운로드.
  • 3. 엑셀 가공받은 엑셀을 가공·조합해 일일 리포트로 정리.
  • 4. 이메일 발송정리된 리포트를 이메일로 사내 발송. 이 일련의 작업에 매일 약 30분 소요.

리포트는 매일 만들어졌지만 실시간성이 없다는 게 가장 큰 한계였습니다. 운영 중 이슈가 생기면 결국 백오피스를 다시 열어 여러 페이지를 오가며 확인해야 했습니다.

해결 과정

기획팀과 함께 사용자별(재무팀·운영팀·경영진) 정보 니즈를 정리하고, 어떤 데이터가 한 화면에 같이 있어야 의미가 있는지부터 정의했습니다. 화면 기획(Figma) 단계에서 필요한 데이터 흐름을 함께 잡고, 그에 맞춰 조회·집계 구조를 설계한 뒤 도메인 단위로 영역을 구성했습니다.

  • 갱신 방식 이원화데이터 성격에 따라 푸시와 폴링을 나눴습니다. 발생 시점을 예측할 수 없고 즉시 반영이 필요한 키오스크 상태 변경·시재 변경 알림은 WebSocket으로 푸시받는 구조로 갔고, 단말과 직접 통신하는 파트가 통신 결과를 DB에 적재하는 시점에 대시보드용 웹소켓으로도 현황을 함께 내려주도록 연동, 이벤트 발생 후 약 3초 이내 화면 반영되도록 구성했습니다.
  • 폴링으로 실시간 현황 갱신거래 현황처럼 지속적으로 갱신되는 데이터는 화면에서 10초 주기로 API를 폴링해 실시간성을 확보했습니다. 짧은 주기로 인한 서버 부하는 폴링 자체를 줄이는 대신, 아래의 캐싱 전략으로 제어했습니다.
  • 캐싱으로 폴링 부하 제어폴링은 주기적으로 호출되다 보니 같은 데이터를 반복 조회하는 부담이 있었습니다. 그래서 응답을 캐싱하되, 캐시 키를 '거래 유형 + 거래일 + 해당 유형의 최신 거래 ID'로 구성했습니다. 핵심은 키에 최신 거래 ID를 포함시킨 것입니다. 새 거래가 들어오면 최신 거래 ID가 바뀌어 키 자체가 달라지므로 자연스럽게 캐시 미스가 나 DB를 새로 조회하고, 새 거래가 없으면 같은 키로 캐시된 응답을 그대로 반환합니다. 별도의 무효화(evict) 로직 없이 키 설계만으로 '데이터가 바뀌었을 때만 갱신'을 구현한 것으로, 짧은 폴링 주기에도 실제 DB 조회는 거래가 실제로 발생한 경우로만 한정했습니다.

이렇게 구성한 화면에 거래 유형별 실시간 현황(원화·외화 거래, 카드 구매·충전·출금, 택스리펀드), 전국 키오스크 상태·알림, 경쟁사 환율 비교를 통합해, 같은 "거래"지만 성격이 다른 흐름을 직관적으로 분리해 볼 수 있게 했습니다.

캐시 키 설계 — 최신 거래 ID를 키에 포함해 자동 무효화
// 키에 최신 거래 ID를 포함 → 새 거래가 생기면 키가 바뀌어 자동으로 새로 조회
// (max id를 빼면 키가 '유형:일자'로 고정돼 그날의 실시간 현황이 갱신되지 않음)
@Cacheable(
  cacheNames = ["dashboardByDay"],
  key = "#type + ':' + #dueDate + ':' + @txRepository.findMaxIdByType(#type)"
)
fun getDashboard(type: TxType, dueDate: LocalDate): DashboardView

// 해당 유형의 최신 거래 1건 id — 거래가 들어올 때마다 값이 커진다
@Query("... ORDER BY trans.id DESC LIMIT 1")
fun findMaxIdByType(type: TxType): Long?

재무팀의 리포트 작성 업무가 일 30분 → 0분(실시간 조회)으로 사라졌고, 의사결정자가 메일을 기다리지 않고 필요한 순간에 직접 대시보드를 열어 상황을 확인할 수 있게 됐습니다.

8개 페이지 → 1개 화면일 30분 → 0분키 설계로 캐시 자동 무효화WebSocket 3초 이내 푸시

'실시간'이 모든 데이터에 같은 방식으로 필요한 건 아니라는 걸 배웠습니다. 즉시성이 필요한 이벤트는 푸시, 주기로 충분한 통계는 폴링으로 나누고, 폴링의 반복 조회 부담은 캐시 키에 최신 거래 ID를 포함시키는 설계로 풀었습니다. 복잡한 무효화 로직 대신 키 설계만으로 '데이터가 바뀌면 자동 갱신'을 구현할 수 있다는 점에서, 문제를 단순하게 푸는 방법을 고민하게 된 경험이었습니다.
